# Era API: deploy notes

One key-based API for the whole ICANERA family (ICANERA, BodaGoEra, SupermarketEra, FarmAgentEra), plus one page for outside
developers. All four apps share one Supabase project, so one key, one registry and one set of limits serve all of them.

**v1** (public, read-only data), **v2** (the business layer) and **developer accounts** (Sign in with Google) are all described here.

- **`/developers`**: a single self-contained page built around the three APIs: **Transactions** (payment requests), **Trading data**
  and **Rider bookings**. Hero with live specimens, one workbench with a tab per API (no sign-up, POST endpoints and the sample-shop
  business sandbox included), business keys, an instant key, and reference docs generated from the live registry
  (`frontend/public/developers/index.html`). Ivory/gold/indigo, light and dark (follows the system, with a toggle). Calls are filed
  under the three APIs by id in the page script (`GROUPS`); anything not matched appears under "More", so a new endpoint still shows up
- **`/api/v1/*`**: the API, served by a thin Vercel function in every app (`frontend/api/v1/[...path].js`)
- an **API tab** in all four developer panels: approve developers, see usage, switch endpoints off, set the gas inputs, switch the
  "verified business" rule (`frontend/public/developers/admin.js`)
- **Business owners mint their own keys** in ICAN: Business, Administration, **Developer API**
  (`frontend/src/components/BusinessApiKeysPanel.jsx`)
- **`/book/<code>` in BodaGoEra**: where a customer confirms a ride or delivery a business requested
  (`mybodaguy/frontend/src/mybodaguy/components/BookingConfirmPage.tsx`)
- **Developer accounts**: "Continue with Google" on `/developers`, a country picker, and an instant sandbox key (section 5 below)
- the database layer: five migrations in `supabase/migrations/`

Merging the code is safe on its own. Until the migrations are applied the developer page shows its built-in reference with a banner
saying the API is "not switched on yet", `/api/v1/ping` says `not_installed`, the owner panel and the dev panel tab say the same, and
nothing else changes. **Nothing here has been applied to your Supabase project by Claude.**

## 1. Apply the database layer (Supabase SQL editor, once)

The easy way: paste **`ERA_API_PASTE_INTO_SUPABASE.sql`** (the five files below, in order, generated by
`node scripts/build-era-api-paste.mjs`) and press Run. Safe to run twice, and safe if you already ran the v1 version of that file.
It only adds `era_api_*` tables, `era_*` functions and a few nullable columns on those tables. It never changes wallets, payments,
rides or stock. (The columns and constraints it relies on in your live project were checked read-only before this was written.)

1. `20261005100000_era_api.sql`: tables, key handling, limits, sandbox, sign-up flow, admin functions
2. `20261005100100_era_api_endpoints.sql`: the public endpoint handlers
3. `20261006100000_era_api_business.sql`: owner keys and scopes, payment and booking requests, idempotency, gas config, the v2 gateway entry point
4. `20261006100100_era_api_business_endpoints.sql`: valuation, supply, convert, gas, integrity chain, journey quotes, product catalogue and the business endpoints
5. `20261007100000_era_api_developer_accounts.sql`: developer profiles, apps owned by a signed-in user, the country, instant sandbox keys (optional: without it the page keeps the no-account flow)

Re-running the endpoint files refreshes descriptions but keeps any endpoint switch or cache time an administrator set.
Rollback (removes v1, v2 and the developer accounts): `supabase/rollback/20261005_rollback_era_api.sql`. It deletes every registered app, key and the call log
and the API's own link tables; your `payment_requests` and `mbg_rides` rows are never touched. To pause without losing anything, use the
master switch in the API tab.

## 2. Who can administer it

Nobody new needs adding if you already have a platform developer or a franchise admin: both count as API admins automatically.
Anyone else is added once, in the SQL editor:

```sql
INSERT INTO public.era_api_admins (user_id, note)
SELECT id, 'founder' FROM auth.users WHERE lower(email) = lower('YOUR-EMAIL');
```

Like the franchise tab, the API tab needs a **real signed-in account**, not the developer panel PIN (the PIN ships in the public app).

## 3. Environment (each of the four Vercel projects)

The gateway needs `SUPABASE_URL` (or `VITE_SUPABASE_URL`) and **one** of `SUPABASE_SERVICE_ROLE_KEY` (preferred) or
`SUPABASE_ANON_KEY` / `VITE_SUPABASE_ANON_KEY`. Optional: `ERA_API_IP_SALT` (any long random string).
Deploy the gateway in **all four** projects before relying on POST: the database accepts the old 5-argument call, but only the v2
gateway forwards bodies and `Idempotency-Key`.

## 4. Check it

```bash
curl https://icanera.space/api/v1/ping
curl https://icanera.space/api/v1/whoami -H "Authorization: Bearer era_test_9a8d0e2b7f4c1a63d5e8b0f2c47a91d3e6b85f0c"
# the business sandbox (a sample shop; creates nothing real):
curl https://icanera.space/api/v1/business/inventory/expiring -H "Authorization: Bearer era_bzt_5c1e7a90b3d24f68a1e0c7d95b2f4a86d3e1c0b7"
```

Then open `/developers/`, press Send, and try the cards.

## 5. Developer accounts: Sign in with Google

`/developers` offers **Continue with Google**. It is the same Supabase Google sign-in ICAN already uses (nothing new to create in Google),
and anyone already signed in to ICAN on the same site is recognised without signing in again. After signing in a developer can:

- see and set **their country**. The picker is the apps' own country list (`frontend/src/constants/countries.js` and
  `frontend/src/services/countryService.js`, flattened to `public/developers/countries.json` by `node scripts/build-era-countries.mjs`).
  The country is filled in, in this order: what they chose, their existing ICAN account (the franchise layer's
  `ican_franchise_country_of()` lookup, so no one is asked twice), then a clearly-marked guess from where they connect from (Vercel's
  `x-vercel-ip-country` header). A guess never overwrites a chosen country.
- **register apps** (up to 5, 3 a day) and get a **sandbox key at once**: no approval, fixture data only, same limits as every sandbox key.
  Rotating it is one click; "Test it" and "Use in playground" are built in.
- reveal a **live key** after you approve the app, exactly like the ticket flow. Administrators see each app's country and whether it came
  from an account or a ticket, next to Approve.

Set up (once):

1. Run migration 5 (it is in the paste file).
2. Supabase, Authentication, **URL Configuration, Redirect URLs**: add `https://<each app's domain>/developers/**` for the four apps
   (and your preview domain if you test there). Without it Google sends people back to the wrong place and sign-in shows an error.
3. Each Vercel project needs `VITE_SUPABASE_ANON_KEY` (or `SUPABASE_ANON_KEY`) as well as `SUPABASE_URL`/`VITE_SUPABASE_URL`. The page
   gets only the **public** URL and anon key from `GET /api/v1/developers/config`; the service-role key is never sent, whatever is set.
   Until a public key is configured the Google card simply does not appear and the no-account flow is the whole page.

The no-account flow (ticket) keeps working unchanged. Each app's sign-in is separate per domain, so a developer who uses
`bodagoera.com/developers` signs in with Google there once; the same Google account maps to the same developer profile everywhere.

## Who gets what, and how

| Key | Looks like | Who issues it | What it reaches |
|---|---|---|---|
| Sandbox | `era_test_…` | the developer, instantly | fixtures for every public endpoint |
| Live | `era_live_…` | the developer, after you approve the app | real public data for the apps you approved |
| Business | `era_biz_…` | the **business owner**, in ICAN | that one business's own data, only the scopes ticked |
| Business test | `era_bzt_…` | the owner, or the published playground key | fixtures for the business endpoints; creates nothing |

Developer keys: register on the page, you review in the API tab (Requests), the developer returns with a ticket and reveals a live key
once. Business keys have no review queue: a business owner (the profile owner, or an active member with the Owner role) mints keys for
their own business with scopes `payments:request`, `payments:read`, `inventory:read`, `cmms:read`, `bookings:request`,
`bookings:read`, an expiry of 1 to 365 days, and (for payment keys) per-request and daily caps. Limits: 10 active keys per business,
5 new keys an hour. Keys are stored only as SHA-256 hashes and shown once.

## What the API exposes

| App | Endpoints |
|---|---|
| Platform | `/whoami`, `/pulse` |
| ICANERA | `/icanera/coin/price`, `/coin/candles`, `/coin/valuation`, `/coin/supply`, `/coin/convert`, `/chain/gas`, `/chain/head`, `/chain/proof/{seq}`, `/fx/rates`, `/countries`, `/tax/{country}`, `/businesses` |
| BodaGoEra | `/bodagoera/stages`, `/districts`, `/ports`, `/fare/estimate`, `/journeys/quote`, `/riders/verify` |
| SupermarketEra | `/supermarketera/stores`, `/catalog`, `/categories`, `/products`, `/clearance`, `/barcode/{code}` |
| FarmAgentEra | `/farmagentera/listings`, `/price-board`, `/crops` |
| Your business (key required) | `POST /business/payments`, `GET /business/payments[/{code}]`, `POST /business/payments/{code}/cancel`, `/business/inventory`, `/inventory/expiring`, `/inventory/summary`, `/business/cmms/overview|assets|stock-alerts|requisitions|work`, `POST /business/bookings`, `GET /business/bookings[/{code}]` |

### The two things that touch money and people only ever *ask*

- **Payment requests** create a normal `payment_requests` row for the business. The payer sees it in their ICAN app and approves with
  their own PIN. The API cannot pay, send or withdraw. Amounts are capped per key; with the "verified business" switch on, only verified
  businesses can mint live payment keys.
- **Booking requests** return a firm quote (the app's own fare maths, including time-of-day surges; any `fare` the business sends is
  ignored) and a confirm link `/book/<code>`. The customer signs in at BodaGoEra and books it themselves; their ride is then linked back
  so the business can track it. Customer and rider identities are never returned to the business.

All POSTs require an `Idempotency-Key` (a retry returns the first answer and creates nothing twice).

### Never exposed, and covered by automated tests

Wallets, balances, transactions, messages; phone numbers, emails, addresses or owners of stores, sellers and riders; supplier identities;
franchise and fee data; one business's data to any other business (tested with two businesses side by side); serial numbers of CMMS assets.

## Things to check or decide

1. **Which public data you publish.** The supplier **catalogue** shows wholesale prices and **stores**/**listings** are public. Each
   endpoint has its own switch in the API tab, Endpoints. Business endpoints can be switched off the same way.
2. **Gas.** `/icanera/chain/gas` estimates a network fee from two numbers you set in the API tab, **Business & gas** (gas price in gwei
   and the coin price in USD). It does not call a node, and every answer says how old those numbers are. Until you set them it answers
   "not configured".
3. **Limits.** Defaults: developers 60 a minute / 5000 a day; business keys have their own limits and caps (see the owner panel).
4. **The published playground keys** (`era_test_9a8d…f0c` and `era_bzt_5c1e…0b7`) are in the page on purpose. They only return fixtures and
   are limited per visitor. If abused, switch the sandbox off in the API tab.
5. **Direct database calls with the anon key.** A determined person could skip the gateway and supply a fake caller hash to dodge per-caller
   limits (per-key and global limits still apply). Setting `SUPABASE_SERVICE_ROLE_KEY` in all four Vercel projects lets you close that:

   ```sql
   REVOKE EXECUTE ON FUNCTION
     public.era_api_request_access(text, text, text, text, text, text[], text, text),
     public.era_api_ticket_status(text),
     public.era_api_issue_key(text, text),
     public.era_api_call(text, text, text, jsonb, text, jsonb, text)
   FROM anon, authenticated;
   ```

   (To undo it, re-run `20261006100000_era_api_business.sql`.) The catalogue and ping stay public either way.
6. **No CAPTCHA** on developer registration (validated, spam-trapped and limited, but the hourly cap can be used up by a determined person).
7. **Browser caching.** Public answers are cacheable for the endpoint's cache time and vary by key. Business answers are never cached.
8. **Not built, on purpose:** moving money, webhooks, usage billing, an email on approval.

## Tests

```bash
supabase/tests/era_api/run.sh            # 363 database checks against a throwaway Postgres (see the script header)
npm test --prefix frontend               # in ICAN: gateway tests and owner-key logic
npm run test:era-api --prefix frontend   # in the other three repos (mybodaguy also has tests/eraBooking.test.js)
node scripts/sync-era-api.mjs --check    # shared files identical in all four repos
node scripts/build-era-api-paste.mjs --check   # the paste file matches the migrations
node scripts/build-era-countries.mjs --check    # the developer page's country list matches the apps' country lookup
```

The database tests apply all five migrations twice, then cover keys (hashed, shown once, rotated, revoked, expired), scopes, limits,
idempotency, owner rights, isolation between two businesses, payment requests (caps, wallets untouched), inventory and expiry maths,
CMMS reads, booking quotes against the booking engine's own formula, the customer-confirm flow, gas, test keys, every admin action,
sealed tables and grants, developer accounts (profile from Google, country sources, isolation between developers, instant sandbox keys, limits), every endpoint against realistic rows, **what must never leak**, a smoke call of every documented example, a
registry-vs-page snapshot check, and that the rollback leaves nothing behind.

## Keeping the four apps in sync

ICAN is the source of truth for the shared files (page, console, gateway, tests, catalogue snapshot). After changing one run
`node scripts/sync-era-api.mjs`. The dev-panel wiring, `vercel.json`, the owner panel (ICAN only) and the booking page (BodaGoEra only)
differ per app and are not synced.

## Adding an endpoint

1. In a new migration, write `public.era_h_<app>_<name>(p JSONB, p_sandbox BOOLEAN) RETURNS JSONB` (return fixtures when `p_sandbox`;
   raise `22023` for bad input, `P0002` for not found, `ERA22` for "understood but not allowed") and add a row to `era_api_endpoints`
   (`access = 'business'` plus a `scope` for private ones; business handlers read the business from `p->>'_business_id'`, never from the request).
2. Add privacy assertions for it to `supabase/tests/era_api/02_endpoints.sql` or `03_business.sql`.
3. Add the migration to `scripts/build-era-api-paste.mjs`, then run `UPDATE_CATALOG=1 supabase/tests/era_api/run.sh`, `node scripts/build-era-api-paste.mjs`, `node scripts/sync-era-api.mjs`.
